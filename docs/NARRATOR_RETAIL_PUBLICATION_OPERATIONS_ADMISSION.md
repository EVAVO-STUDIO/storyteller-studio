# Narrator retail publication operations admission

## Purpose

This boundary carries the exact admission-bound Audio Studio narrator from
post-publication monitoring into refresh evidence intake, monitor mutation,
incident creation and verified recovery.

The generic audiobook publication monitor, evidence inbox and alert engines
remain authoritative for publication health. This module does not replace or
fork them. It adds the narrator admission envelope that those generic engines
cannot infer on their own.

## Admission boundary

Operational evidence begins from a valid
`AdmittedNarratorRetailPublicationMonitor`.

The request retains the exact:

- project and book;
- Audio Studio narrator profile identifier, revision and profile hash;
- narrator profile admission hash;
- admitted casting fingerprint and casting fingerprint;
- approved narrator retail listing;
- accepted retailer-status evidence;
- public Audible audiobook ASIN;
- generic monitor identifier, revision and fingerprint;
- approved listing identity and required regions; and
- latest admitted publication verification.

A generic monitor or generic publication verification is not sufficient to
enter this boundary by itself.

## Evidence request

`createAdmittedNarratorRetailPublicationEvidenceRequest` creates one immutable
request for the current admitted monitor revision.

The request embeds the generic evidence request generated by the existing
publication evidence inbox engine. The admitted wrapper proves which narrator,
listing and public product the generic request belongs to.

A request does not acquire evidence, run a browser, refresh a monitor, create an
incident, repair a listing or publish anything.

## Evidence intake

`submitAdmittedNarratorRetailPublicationEvidence` accepts only a complete
`AdmittedNarratorRetailPublicationVerification`.

Before the generic evidence inbox receives the verification, the operations
boundary reopens and validates:

- the exact narrator profile pin;
- adapted or zero-shot admission provenance;
- the exact admitted casting;
- the complete approved listing fingerprint;
- listing identity identifier and fingerprint;
- retailer acceptance lineage;
- total production-job count;
- required-region set; and
- the exact Audible audiobook ASIN.

Cross-title evidence, replacement narrators, another listing, another public
product and another ASIN fail before evidence intake.

The underlying generic inbox still validates request revision, chronology,
freshness, required regions, listing identity and independent human
verification.

## Refresh operation

`applyAdmittedNarratorRetailPublicationEvidence` performs one deterministic
in-memory domain transition.

It:

1. revalidates the admitted evidence;
2. records the generic publication verification through the existing monitor
   engine;
3. rebuilds the admitted narrator monitor with the new immutable verification
   history;
4. acknowledges the generic inbox item only after the resulting monitor proves
   exact consumption; and
5. creates an admitted incident when the new transition is actionable.

The operation is an immutable evidence record. Persistence, worker leasing,
network acquisition and transaction coordination remain separate private
runtime concerns.

## Stale evidence

`markAdmittedNarratorRetailPublicationEvidenceStale` uses the existing generic
monitor freshness rule.

It does not invent a narrator verification. The admitted verification history
remains unchanged. The monitor receives the governed stale transition and one
admitted evidence-stale incident.

Calling the operation before the refresh deadline fails through the generic
monitor rule. Calling it on an already stale admitted monitor is rejected
rather than creating another indistinguishable incident.

## Incident creation

An admitted incident wraps the existing generic
`AudiobookRetailPublicationAlert`.

The generic alert engine remains authoritative for:

- identity-mismatch classification;
- publication-unavailable classification;
- regional-degradation classification;
- evidence-stale classification;
- severity;
- finding codes;
- deterministic email notification identity;
- bounded delivery attempts;
- acknowledgement; and
- verified-recovery resolution.

The admitted wrapper additionally binds the incident to the exact narrator
profile, admission, casting, listing and Audible ASIN that produced the monitor
transition.

Healthy refreshes and verified recoveries do not create new incidents.

## Verified recovery

`resolveAdmittedNarratorRetailPublicationIncident` accepts only a later
admitted narrator monitor with:

- the same project and book;
- the same exact narrator voice pin;
- the same profile admission and casting;
- the same admitted listing;
- the same generic monitor identity;
- the same listing identity and required regions;
- the same Audible audiobook ASIN;
- a later monitor revision;
- `healthy-live` publication health; and
- a latest `recovery` transition.

The underlying generic alert engine then records the verified recovery.

A monitor for another title, narrator, listing or public product cannot resolve
the incident even if its public health is healthy.

## Adapted and zero-shot provenance

Adapted and zero-shot narrators use the same operational contract.

They do not become interchangeable.

An adapted narrator retains its training campaign, capability, checkpoint,
dataset, lock and model-tree lineage through its existing profile admission.
A zero-shot narrator retains an explicit absence of training provenance.
Neither mode can borrow the other mode's evidence.

## Immutable lineage

Every request, evidence receipt, operation and incident is fingerprinted over
its complete source chain.

Recomputing an outer fingerprint cannot substitute:

- another narrator;
- another title;
- another listing;
- another retailer acceptance;
- another generic monitor;
- another verification;
- another public product; or
- another recovery.

The generic evidence request, inbox item, monitor entry, transition and alert
fingerprints remain independently validated as well.

## Authority boundary

This module records evidence and derives publication health.

It always keeps these flags false:

- `automaticRefreshAuthority`;
- `automaticRemediationAuthority`;
- `automaticRepublishAuthority`; and
- `publicationAuthority`.

Evidence availability does not authorize refresh execution by an arbitrary
runtime. A refresh result does not authorize listing edits. An incident does
not authorize remediation. A recovery does not authorize republishing.

Human or private operational systems must act through their own explicit,
audited boundaries.

## Private runtime boundary

The normal web and protected API runtimes must not import or invoke these
mutation controls.

A private worker or CLI may later coordinate persistence and acquisition, but
it must preserve:

- exact admitted-monitor revision checks;
- optimistic storage concurrency;
- evidence freshness;
- bounded network timeouts;
- private route and credential resolution;
- deterministic alert idempotency;
- no raw storefront evidence in public output; and
- no automatic remediation.

This tranche deliberately stops before adding a network browser, scheduler,
persistent admitted-monitor store or alert-delivery runtime.

## Public projection

Public projections expose only bounded retail state:

- book identity;
- Audible marketplace and audiobook ASIN;
- intended display title and narrator credit;
- expected monitor revision;
- required regions;
- current publication health;
- verification status and dates;
- transition kind;
- incident category and severity;
- notification delivery status;
- whether evidence was acknowledged; and
- whether a verified recovery resolved the incident.

They omit:

- project identifiers;
- narrator profile identifiers and hashes;
- profile admission and casting fingerprints;
- training evidence;
- reviewer and observer identities;
- generic monitor and listing identifiers;
- retailer references;
- evidence request and inbox identifiers;
- source reference hashes;
- recipient route hashes;
- public product, sample and cover reference hashes; and
- complete nested source evidence.

## Output boundary

A successful operation proves only that the supplied evidence forms a valid
admission-bound domain transition.

It does not prove that a network acquisition ran, that persistence succeeded,
that an alert was delivered, that a retailer corrected a problem, or that
future storefront availability will remain healthy.

It does not guarantee future availability.
