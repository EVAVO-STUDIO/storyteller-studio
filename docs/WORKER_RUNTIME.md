# Private Worker Runtime

The Storyteller worker is a dedicated non-HTTP process. It composes the durable generation queue, immutable generation material, transactional budget control, provider adapters, lease heartbeat, private object storage and artifact registry without exposing execution controls through the web application or operator API.

## Disabled by default

`STORYTELLER_WORKER_MODE` defaults to `disabled`. In disabled mode the process does not evaluate queue paths, provider credentials, provider configuration or execution settings and does not create persistence directories.

Enabled modes are:

- `once` — process available work until the queue is idle, then stop;
- `continuous` — keep polling until a process signal requests shutdown.

## Fail-closed storage

The initial runtime supports only one isolated host using the existing file-backed contracts. Enabled mode requires:

- `STORYTELLER_QUEUE_DRIVER=file`;
- `STORYTELLER_ARTIFACT_DRIVER=file`;
- a private `STORYTELLER_DATA_DIR`;
- a valid worker identity and verifier identity.

Production additionally requires all three explicit acknowledgements:

- `STORYTELLER_FILE_QUEUE_SINGLE_HOST=true`;
- `STORYTELLER_FILE_ARTIFACT_STORE_SINGLE_HOST=true`;
- `STORYTELLER_FILE_WORKER_SINGLE_HOST=true`.

The acknowledgements do not make file persistence distributed. They prevent an accidental serverless or multi-instance deployment from presenting local locks as cross-host coordination.

## Isolated persistence

The runtime derives three internal roots beneath the configured data directory:

- `generation-queue` for queue, immutable generation-material and project budget-account envelopes;
- `artifact-registry` for revisioned artifact metadata;
- `private-objects` for content-addressed generated bytes.

None of these paths are returned by public runtime summaries or written to normal API responses.

## Provider registration

Provider registration is explicit and conditional. The worker first resolves its own runtime mode. Only an enabled worker evaluates provider-specific configuration.

ElevenLabs is currently the first concrete provider boundary. `STORYTELLER_ELEVENLABS_ENABLED` defaults to `false`. When false, the provider registry remains empty and does not parse model policies, pricing records, voice bindings, pronunciation dictionaries or data-policy records.

When true, the provider is registered only after complete model, pricing, voice, privacy and credential configuration validates. The credential binding must map provider id `elevenlabs` to a server environment-variable name; possessing `ELEVENLABS_API_KEY` alone does not register the provider.

The provider resolver rejects malformed or missing records, expired pricing, unsupported output controls, unapproved v3 production, non-premade local voice bindings and invalid privacy declarations before constructing the adapter.

## Provider preflight

The worker refuses to poll the queue when no provider adapter is registered. Every registered adapter must have a server-side credential and must return a capability snapshot whose provider identity, adapter version and fingerprint match the executing adapter.

Credential bindings map a provider identifier to an environment-variable name. The mapping may be configured through `STORYTELLER_WORKER_CREDENTIAL_BINDINGS`; secrets remain in their referenced server environment variables and are never copied into runtime summaries, queue state, artifacts or logs.

For ElevenLabs, preflight inspects the configured model records and the remote voice category before queue polling. A missing credential, reduced model limit, unavailable model or remote category other than `premade` stops worker startup. A successful preflight on an empty queue reads model and voice metadata but performs no synthesis call.

Enabling the worker without any valid provider still fails with `WORKER_PROVIDER_ADAPTERS_REQUIRED` rather than pretending generation is available.

## Required budget control

The dedicated runtime creates `FileBudgetLedger` and `FileGenerationBudgetController` from the private queue-state store and constructs `GenerationWorkerService` with `requireBudget: true`.

This is not an optional production feature. For every claimed job:

1. immutable material is resolved and revalidated;
2. the controller requires a cost policy;
3. the matching project and currency account must exist;
4. the maximum approved cost is reserved;
5. provider execution may begin only after reservation succeeds.

Missing account, missing policy, insufficient capacity or reservation conflict blocks the queue item before provider invocation.

The worker settles through the internal typed queue-transition callback:

- actual cost is committed after artifact admission and before queue completion;
- configuration block or retry without a provider attempt releases the reservation;
- partial successful work commits observed cost;
- attempted work without trustworthy cost evidence commits the maximum conservatively;
- forced abort or ownership loss settles interrupted work conservatively.

Budget account, reservation and settlement identities remain absent from runtime summaries and ordinary API responses.

## Bounded execution

The worker validates bounded values for:

- concurrency;
- queue poll interval;
- lease duration;
- heartbeat interval;
- provider timeout;
- outcome history;
- shutdown grace period;
- provider preflight and response limits.

The heartbeat interval must remain below half the lease duration. Provider execution uses the same live clock as heartbeat renewal, budget settlement and terminal queue transitions.

## Process signals

The process subscribes to `SIGINT` and `SIGTERM` only inside the worker lifecycle.

The first signal:

1. stops new claims;
2. allows active jobs to keep renewing their leases;
3. schedules a bounded forced-abort deadline;
4. exits after active jobs finish.

A second signal or an expired shutdown deadline aborts active provider work. Interrupted claims are not falsely completed. They remain recoverable through lease expiry and the queue reaper. Any active budget reservation is settled conservatively before the worker records its safe operational outcome.

Signal listeners and shutdown timers are always removed after the worker stops or fails.

## No HTTP execution surface

The worker package imports no HTTP server and opens no listening port. The normal API and web application must not import:

- the worker service;
- generation material storage;
- budget reservation or settlement;
- provider configuration or execution;
- lease claiming or heartbeat controls;
- private object writes;
- artifact verification or completion.

Operational control belongs to deployment process management and restricted service identity, not a public route.

## Safe operational output

Process output is limited to redacted configuration and lifecycle summaries. It may include mode, concurrency, timing limits, provider count and aggregate job outcomes. It excludes:

- worker and project identifiers;
- data-directory paths;
- credential environment-variable names and values;
- provider model-policy and pricing records;
- voice and pronunciation-dictionary identifiers;
- manuscript text and direction;
- voice profile identifiers;
- provider request identifiers;
- private object locators;
- budget account or reservation identifiers;
- lease tokens and hashes.

## Production migration

The same runtime boundary will later compose:

- PostgreSQL transactional claims, material records and budget accounts;
- private cloud object storage;
- durable budget-reservation renewal linked to worker ownership;
- provider pricing snapshots and commercial reconciliation;
- workload identity and managed secret rotation;
- distributed metrics and tracing without manuscript content;
- autoscaling based on safe queue aggregates;
- dead-letter review and operator recovery.

Provider registration and budget reservation are separate gates. The runtime does not weaken either merely to make the process start.
