# Pre-provider Generation Budget Control

The generation-budget controller connects an exclusive queue attempt to the transactional budget ledger. Its purpose is to move commercial approval ahead of provider invocation while preserving a second evidence-based cost check after execution.

## Admission before provider work

A worker must have all of the following before reserving budget:

- an active exclusive queue claim;
- immutable generation material for the same job, project and segment;
- a valid cost policy containing one currency and maximum approved job cost;
- a provisioned project budget account with enough available capacity;
- a bounded provider timeout.

The controller derives the reservation from the queue item and current attempt. Network retries of the same attempt return the same reservation. A later queue attempt receives a different reservation.

Provider execution must not begin until this reservation succeeds.

## Reservation duration

The reservation lifetime is the greater of:

- the configured base reservation lifetime; or
- provider timeout plus a bounded safety margin.

This keeps the hold valid through the expected provider call without relying on a short queue lease. The reservation still has a bounded expiry, so a crashed process cannot hold capacity indefinitely.

A future distributed worker will renew reservation ownership alongside the queue heartbeat. The initial controller deliberately uses a conservative duration rather than falsely presenting two independent renewals as one transaction.

## Queue-transition settlement

The generation worker emits an internal typed transition only after it knows the provider and artifact outcome.

### Complete

A completion transition occurs only after:

1. provider execution produced the complete candidate set;
2. generated bytes were stored privately;
3. artifact integrity verification passed;
4. the exact artifact bundle passed queue admission.

The transition must include finite cost evidence in the reservation currency. The controller commits the actual micro-unit amount before `queue.complete` is allowed to run. Actual cost above the reservation blocks completion.

### Block before provider invocation

When no provider was attempted, the controller releases the reservation before the queue item is blocked. Missing adapters, credentials or other configuration failures therefore do not consume project budget.

### Retry before provider invocation

A retry transition with no provider attempt also releases capacity. A later queue attempt creates its own reservation.

### Partial or unsuccessful provider work

When a provider was attempted, the system must not assume the call was free.

- Valid observed cost is committed.
- Valid partial result cost is committed even when the candidate set is incomplete.
- Observed cost above the approved reservation is capped at the reservation and marked conservative for reconciliation.
- A provider attempt without trustworthy cost evidence commits the full reservation conservatively.
- Successful output with missing or mismatched cost evidence also commits the full reservation conservatively.

This avoids hiding potentially incurred spend. A later commercial reconciliation can create an explicit adjustment rather than rewriting the original reservation history.

## Interrupted work

An abort, ownership loss or unexpected worker error may occur before a typed queue transition is emitted. The budget session exposes `settleInterrupted` for this boundary.

Interrupted work conservatively commits the reserved maximum. This may overstate spend temporarily, but it cannot understate an external provider charge or make budget available twice. Operational reconciliation must be explicit.

## Settlement idempotency

A budget session accepts one terminal settlement. Repeated calls return the same settlement rather than creating a second ledger mutation.

The underlying ledger independently enforces idempotent commit or release operations. A conflicting settlement amount is rejected.

## Public projection

The safe reservation projection exposes only:

- currency;
- maximum micro-unit amount;
- expiry;
- reservation fingerprint.

It omits project, job, queue item, attempt, reservation identifier, actor, credential, provider request and object-storage identity.

## Internal-only boundary

The controller is an internal worker dependency. Normal web and API runtimes must not import it or expose routes for:

- reserve;
- renew;
- settle;
- release;
- interrupted-work settlement.

A future operator UI may show aggregate budget availability through a separately authorised read model. It must not receive executable reservation controls.

## Production sequence

The intended worker sequence is:

```text
exclusive queue claim
→ immutable material resolution
→ rights and capability revalidation
→ budget reservation
→ provider execution
→ private artifact ingestion
→ artifact admission
→ budget settlement
→ queue terminal transition
```

The ordering is deliberate. Queue completion must never occur before budget settlement, and provider invocation must never occur before reservation.

## Production migration

The file controller is suitable only for one isolated host. Multi-instance production will retain the same transition contract while using:

- PostgreSQL account and reservation transactions;
- durable worker and reservation ownership;
- provider quote snapshots;
- reservation heartbeat renewal;
- governed adjustments and refunds;
- reconciliation queues for conservative settlements;
- anomaly alerts and project-level spend circuit breakers.

No production provider adapter should be enabled until the worker service composes this controller and the full integration tests prove reservation-before-invocation and settlement-before-completion.
